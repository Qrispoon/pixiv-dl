## 1. 结论摘要

1. **技术路线成立**：Pixiv 移动端 App API（`app-api.pixiv.net`）+ OAuth refresh_token 是本类工具（pixivpy、gallery-dl）多年沿用的稳定路线；本机经代理实测端点存活、OAuth 客户端凭据仍被接受、搜索与图片 CDN 可用。
2. **收藏数过滤：普通账号只能在本地做，Premium 账号可用服务端参数加速**。App API 的搜索确实接受 `bookmark_num_min` / `bookmark_num_max` 参数（活跃项目 pixiv-cli 的 `internal/pixiv/api/routes.go` 明确声明，`sdk/pixiv/search_filters.go` 实际发送），但其 `searchfilter` 包把「server 策略」限定为 **已验证的 Premium 会员**（`ErrBookmarkNonPremium`），非会员只能本地过滤。正确设计是「搜索分页 → 读取 `total_bookmarks` → 本地过滤」为兜底；检测到 Premium 时改为「服务端参数 + 本地复核」，可把扫描量降低一个数量级。
3. **主要成本是「扫描」而不是「下载」**：搜索接口每页 30 条、`offset` 上限 5000（实测 5010 即返回 0 条），且日期切片存在已知漏抓风险（gallery-dl #8843）。大标签（实测「初音ミク」总作品数 62 万+）全量扫描需 2 万+ 次请求，按 2 秒/请求约 11 小时。方案需提供日期范围/日期切片、页数上限，以及 Premium 账号的服务端收藏过滤 + `popular_desc` 提前止损。
4. **下载环节简单可靠**：`i.pximg.net` 图片必须带 `Referer: https://www.pixiv.net/`（实测 200 vs 403），原图 URL 规律稳定，多页作品有 `pages`/`meta_pages` 接口；动图 ugoira 有元数据 + zip，且 **GIF/MP4 转换已实测**（ffmpeg 9.0.2：100 帧 → 540×304 GIF 4.02 MB / 4.2s，同源 MP4 仅 326 KB）。
5. **Windows 上没有 Python 环境，Node.js 26 已有**；Node 内置 `fetch` 配合 `--use-env-proxy`（或 `NODE_USE_ENV_PROXY=1`）可直接走 HTTP 代理（已实测），因此**零运行时依赖**实现可行，只对动图转码可选依赖 `ffmpeg`。

**可行性判定：P0 通过，可以进入开发（M1 见 [`02-项目方案.md`](02-项目方案.md)）。**

## 3. 逐项证据与解读

### 3.1 域名与代理层

| 域名 | 用途 | 实测 | 备注 |
| --- | --- | --- | --- |
| `www.pixiv.net` | Web Ajax（匿名/Cookie 路线）、作品页 | 200 | Cloudflare 前置；**只带 User-Agent 会被 302/403**，补齐 `Accept`/`Accept-Language`/`Sec-Fetch-*` 后 200（已实测） |
| `app-api.pixiv.net` | 主路线 App API | 400（无 token，预期） | 需要 `Authorization: Bearer`，并带 App 特征头（`App-OS`、`App-Version`、`User-Agent: PixivAndroidApp/…`、`Referer: https://app-api.pixiv.net/`） |
| `oauth.secure.pixiv.net` | 换取/刷新 access_token | 400 `invalid_grant` | 说明 `client_id/client_secret` 与 `X-Client-Time`/`X-Client-Hash` 校验通过 |
| `i.pximg.net` | 原图/动图 zip | 200 / 403（无 Referer） | 下载必须带 `Referer: https://www.pixiv.net/`；代理需覆盖该域名 |

**结论**：你的代理（127.0.0.1:10090）为 HTTP 代理，四个域名全部可经其访问；工具需支持 `HTTPS_PROXY`/`HTTP_PROXY` 并统一走代理，不能依赖系统代理（本机 WinHTTP 显示「直连」，直连 Pixiv 不通）。

### 3.2 鉴权（OAuth）

- Pixiv 移动端 OAuth 端点仍在工作：`POST https://oauth.secure.pixiv.net/auth/token`，表单字段 `client_id`、`client_secret`、`grant_type`、`refresh_token`，请求头需 `X-Client-Time`（UTC ISO8601）与 `X-Client-Hash = md5(X-Client-Time + hash_secret)`。
- 公开的 Android App 凭据（pixivpy、gallery-dl 均内置）当前仍被接受：`client_id=MOBrBDS8blbauoSck0ZfDbtuzpyT`、`hash_secret=28c1fdd1…bae2c`。**这是逆向得到的凭据，Pixiv 可随时更换或针对其封禁**，属于本方案最大外部依赖。
- 登录页入口实测：`GET https://app-api.pixiv.net/web/v1/login?code_challenge=<43字符>&code_challenge_method=S256&client=pixiv-android`
  → `302` 跳转 `accounts.pixiv.net/login?...return_to=…/web/v1/users/auth/pixiv/start?code_challenge=…`。登录后 Pixiv 依次经过 `accounts.pixiv.net/post-redirect` → `app-api.pixiv.net/…/auth/pixiv/start`，最终 **302 到 `pixiv://account/login?code=…`**（唤起 App 的自定义协议）。
- **本机实测的坑**：没有注册 `pixiv://` 协议处理器时，浏览器会停在 `post-redirect` 中转页，地址栏看不到 code；code 实际在该次 `start` 请求的 302 `Location` 里。可用两种方式取到：① DevTools → Network 找到 `start` 请求 → Response Headers → `location`；② 用浏览器会话的 `PHPSESSID` 让脚本直接请求 `start`（`scripts/login.mjs --cookie "PHPSESSID=…"`，已实现）。
- 该流程的现成实现（一手源码依据）：gallery-dl 的 `gallery_dl/extractor/oauth.py`（`OAuthPixiv` 类）与 `gallery_dl/extractor/pixiv.py`（`PixivAppAPI` 类）；pixiv-cli 则注册 `pixiv://` 处理器自动接回调。本机已留存源码副本：`（本地参考）gallery-dl-oauth.py`、`（本地参考）gallery-dl-pixiv.py`、`（本地参考）pixiv-cli-repo/`。
- 本仓库已提供该流程的零依赖脚本 [`scripts/login.mjs`](../scripts/login.mjs)：支持 `--open` 打开登录页、粘贴 `pixiv://`/回调 URL/code、以及 `--cookie` 免抓包方式；token 保存到仓库根 `.secrets/`（与运行目录无关）。
- **登录态已实测（2026-11-14）**：账号 `demo-account` 登录成功，`refresh_token → access_token` 正常，`is_premium=false`；access_token 可正常调用 app-api 搜索（详见 3.3）。脚本 `--check` 显示 token 可用。
- 关键工程限制（gallery-dl 源码注释与实测）：**授权码约 30 秒内必须兑换，且只能用一次**；`--cookie` 方式没有这个时间压力（challenge 由脚本运行时新生成、立即换取）。

### 3.3 搜索、分页与收藏数

App API 搜索（`/v1/search/illust`）：

- 参数：`word`、`search_target`（`partial_match_for_tags` / `exact_match_for_tags` / `title_and_caption`）、`sort`（`date_desc` / `date_asc` / `popular_desc`）、`filter`（`for_ios` / `for_android`，实测**不会**隐藏 R-18；R-18 是否出现由账号设置决定，实测结果里 `x_restrict=1` 与 `0` 同时存在）、`offset`、`start_date`/`end_date`、`duration`、`search_ai_type`（`0`=排除 AI、`1`=包含，不是「只看 AI」）。
- 返回：`illusts[]`（含 `id`、`user.id/name/account`、`total_bookmarks`、`page_count`、`meta_pages[].image_urls.original`、`illust_ai_type`、`x_restrict`）与 `next_url`。
- **实测（2026-11-14，非 Premium 账号）**：
  - 每页 **30 条**，`total_bookmarks` 直接可用；
  - `offset=4980` → 200、30 条、`next_url` 有；`offset=5010` → 200、**0 条**；即 **5000 是硬上限**（不是 5001 才断，也不报错，只是空结果）；
  - `start_date/end_date` 日期过滤有效（单日窗口返回的作品日期均在该日）；
  - `bookmark_num_min=5000` **被静默忽略**（返回结果未过滤）→ 非 Premium 必须本地过滤；
  - `sort=popular_desc` 对非 Premium **退化为时间排序**（首屏 `total_bookmarks` 全 0、按最新发布排序）→ 不能当加速手段；
  - 同一日期的 Web `total` 在多次运行间会小幅漂移（7957 vs 7960）→ 覆盖核对只能作近似基准。
- `offset` 上限 **5000**（≈166 页/窗口）。依据：pixivpy issue #69 与本次实测；gallery-dl `pixiv.py` 第 1399–1406 行在 `offset >= 5000` 时自动改 `end_date` 并重置 offset（**日期切片**）。注意：该切片在超大样本上被报告会**漏抓/提前停止**（gallery-dl issue #8843，2026-01 至今 open），不能假设「翻页到空就一定抓全」。
- **覆盖率的两个已知缺口**（需在方案中如实标注）：① 日期切片自身的漏抓风险（#8843）；② app-api 返回结果可能比 web 页面少（pixivpy #277：同一画师 web 15 件、API 14 件），属上游索引差异，工具无法完全消除。
- 收藏数过滤：
  - App API 的 `search_illust` 接受 `bookmark_num_min` / `bookmark_num_max`（活跃项目 pixiv-cli 的 `internal/pixiv/api/routes.go` 定义了这两个参数名，`sdk/pixiv/search_filters.go` 会写入请求）；但 pixiv-cli 的 `internal/pixiv/searchfilter/bookmark.go` 把「服务端过滤」策略限定为 **已验证 Premium 会员**，非会员走本地核对（`ErrBookmarkNonPremium`）。即：**参数存在，但非 Premium 账号不应依赖其生效**。
  - Web Ajax 搜索也有 `blt`（最低收藏）/`bgt`（最高收藏），第三方文档同样标注 **Premium account authorization is required**，且该文档已声明长期未维护。
  - 官方帮助页把「按热门顺序搜索」列为 Premium 权益。→ 设计上以「本地 `total_bookmarks` 过滤」为正确性兜底；Premium 账号额外启用 `bookmark_num_min/max` 与 `sort=popular_desc` 减少扫描量，并对服务端结果再做一次本地校验（防止参数被静默忽略）。
- 匿名 Web 搜索（`https://www.pixiv.net/ajax/search/artworks/{keyword}`）：实测可用、60 条/页、`p=100` 仍可翻页，但**列表不含收藏数**，必须逐作品请求 `/ajax/illust/{id}` → 请求量放大约 60 倍，只适合作为兜底路线或小规模任务。

### 3.4 图片下载

- 原图 URL 形如 `https://i.pximg.net/img-original/img/2022/08/11/23/46/14/100412238_p0.png`；多页作品后缀 `_p0`、`_p1`…；扩展名可能是 `jpg/png/gif`。
- 实测：带 `Referer: https://www.pixiv.net/` → 200；不带 → 403。下载器必须统一注入 Referer，且 `fetch` 跟随重定向时也要保留。
- App API 的 `meta_single_page.original_image_url` / `meta_pages[].image_urls.original` 可直接给出原图地址；Web 路线的 `/ajax/illust/{id}/pages` 同样可给（匿名可用，已实测）。
- 风险：作品被删除/私有化（404）、R-18 且账号未开年龄限制（返回 `limit_sanity_level` 占位图或 403）、原图 URL 失效（可回退 `large`/`master1200` 并记录）。
- 受限作品（sanity/年龄限制）可能只返回 `limit_*` 占位图，gallery-dl 的提示是「需要登录后的 cookie」；即**仅 refresh_token 可能拿不到这类原图/原始 ugoira zip**（此点为社区/源码推断，未实测）。v1 先按「标记 restricted 并跳过」处理，cookie 兜底列为可选增强。

### 3.5 动图（ugoira）

- 实测：`GET https://www.pixiv.net/ajax/illust/{id}/ugoira_meta`（匿名可用）返回 `frames[]`（`file` + `delay` 毫秒）与 `originalSrc`（1920×1080 zip）、`src`（600×600 zip）。
- zip 可经代理下载（实测 HTTP 200，约 3.4 MB / 100 帧）。
- **GIF 转换已实测可行（本机 ffmpeg 9.0.2 + Windows 自带 bsdtar 3.8.9）**：取作品 `151837674`（100 帧，delay 40/50ms）→ 下载 zip → `tar -xf` 解帧 → 按 `frames[].delay` 生成 concat 清单 → ffmpeg 两遍（`palettegen` + `paletteuse`）：
  - 540×304：**4.02 MB**，100 帧 / 4.2s，帧延迟正确（40ms 采样验证），转换约 1 秒；
  - 1920×1080 原尺寸：4.27 MB（本例画面简单；复杂画面会明显更大）；
  - 同源 540 宽 H.264 MP4：**326 KB**（约 GIF 的 1/12，画质更好）。
  - 样例 GIF 已本地留存，未随仓库分发。
- 交付形式：**按用户选择，工具默认转 GIF**（本机 ffmpeg 已实测；可配 `--ugoira-width`，默认 540）；`--ugoira mp4` 出视频，`--ugoira zip` 保留原始 zip。`tar`/`ffmpeg` 缺失时降级为 zip 并明确提示。

### 3.6 运行时与代理能力（Node.js）

- 本机：Node v26.13.0；无 Python（`python`/`py` 均不可用）→ 不适合直接复刻 pixivpy/gallery-dl，自研 Node CLI 更合适。
- 实测：`NODE_USE_ENV_PROXY=1` + `HTTPS_PROXY/HTTP_PROXY` 时，Node 内置 `fetch` 请求 Pixiv 返回 200；`node --use-env-proxy` 等效。
- 实测：**进程启动后再修改 `process.env.HTTPS_PROXY` 无效**（仍直连超时）→ `--proxy` 参数需通过「设置环境变量后重新 spawn 自身」或启动前注入环境变量实现。
- Node 内置代理仅支持 HTTP(S) 代理，**不支持 SOCKS5**；Clash/v2ray 的 mixed/HTTP 端口（如 7890、本机 10090）可用。若将来要支持 SOCKS，需引入 `undici` + socks agent（会增加依赖，非首版必需）。
- 零运行时依赖可行：`fetch`、`node:fs`、`node:readline`、`node:util parseArgs`、`node:test` 均为内置。

### 3.7 同类工具（prior-art）

- **没有活跃的 Node.js 现成库**：`pixiv-app-api`（2020 停更）、`pixiv-api-client`（2024 停更），因此自研 HTTP 封装是必要成本。
- **可直接参照的两个活跃实现**：
  - [gallery-dl](https://github.com/mikf/gallery-dl)（Python，活跃）：refresh_token、标签搜索、日期切片、ugoira、去重 archive，是最完整的参考（本机有源码副本）。
  - [pixiv-cli](https://github.com/FlanChanXwO/pixiv-cli)（Go，2026-11 仍日更，132★）：同样是 App API + 浏览器 OAuth，支持按收藏数过滤（`bookmark_num_min/max`，Premium 走服务端、非会员本地核对）、GIF/APNG ugoira、下载报告；本方案的分页/过滤/限流设计与它互相印证。
- 结论：这类工具在 2026 年仍能正常工作，说明路线成熟；同时它们的存在也说明「登录获取 token」是所有人都要手动过一次的坎。

详细调研见 [`docs/06-同类工具调研.md`](06-同类工具调研.md)。

### 3.8 覆盖率问题的底层原理与可修复程度

**结论：不是"无法修复"，而是分成「可消除」「可补漏」「不可保证」三层。默认方案能把错误从"必然漏一大截"降到"可核对、边界误差趋近 0"，但不能承诺 100%。**

#### 3.8.1 为什么有 5000 上限

Pixiv 搜索是典型的 offset/limit 分页：客户端传 `offset=0,30,60…`，服务端返回一页。深分页对服务端成本高（要跳过 offset 条记录），也对爬虫不友好，因此服务端对 `offset` 有硬上限（社区实测 App API 为 5000，见 pixivpy #69）。越过上限时返回空/错误，**与账号权限无关**，不是登录能解决的。

绕过方式只有「缩小每次查询的结果集」：给定标签后，用 `start_date`/`end_date` 把作品按发布日期切成若干窗口，使每个窗口内作品数 < 5000，offset 就不会触顶。gallery-dl 就是这么做的（`pixiv.py` L1399–1406）。

#### 3.8.2 为什么日期切片仍会漏（三个根因）

1. **日期粒度是天，排序键是秒**。`start_date/end_date` 只到 `YYYY-MM-DD`，而搜索结果按 `create_date`（秒级）排序。若某一天的作品数就超过 5000，**无论怎么切日期窗口都无法把这一天拆开** → 该窗口必然只能枚举前 5000 条。
2. **边界/并列/重复**。同一天的作品被切到两个窗口时，靠「取最后一条的日期 +1 天」来衔接，若同秒并列、排序不稳定，边界处会重复或跳过；gallery-dl #8843 的实测正是：约 2.1 万作品只抓到 1.26 万（≈60%），且日志显示它「提前停」和「跳过一整层」。该 issue 至今 open。
3. **扫描期间数据在变**。新作品发布、作品删除/私有化会让 offset 的含义漂移；固定窗口（`start/end` 不变）能缓解，但无法消除。
4. **app-api 与 web 索引不完全一致**。pixivpy #277：同一画师 web 15 件、API 14 件。这属于上游差异，任何基于 app-api 的工具都无法完全消除。

#### 3.8.3 我们能修到什么程度（分层设计）

| 层级 | 做法 | 成本 | 效果 |
| --- | --- | --- | --- |
| L0 必做 | 窗口边界重叠一整天 + 全量 pid 集合去重 + 固定窗口内不漂移 + 断点续跑 | 0 额外请求（仅重叠页） | 消除「切片边界丢失」，把 #8843 那类错误降到接近 0 |
| L1a 超限日「双向枚举」 | 某一天被 offset 上限截断时，对同一天再跑一次 `sort=date_asc`（从旧到新取前 5000 条），与 `date_desc`（从新到旧取前 5000 条）取并集；**并用两个方向的边界时间戳判断是否真的接上**：`asc` 最新一条的时间 ≥ `desc` 最旧一条的时间 ⇒ 无中间缺口 | 该天 +166 次搜索请求 | 单日可见作品 ≤约 10000 条时可完整覆盖；>10000 时双向枚举也留中间缺口，需靠 Premium 或如实报告 |
| L1b 覆盖核对与有限补漏 | 用 Web Ajax 搜索（`scd/ecd` 精确日期 + `total`）得到「该窗口应有多少条」的下界，与 app-api 枚举数对比；有差额时，再从 Web 前约 600 条里差分出 app-api 没返回的 id（只能覆盖 ≤600 条/日的缺口），逐个补详情/下载 | 每窗口 1 次 Web 请求；有缺口时 ≤10 次采样 + 每件 1 次详情 | 把「未知漏抓」变成可量化差额；能定位到 id 的缺口可补，定位不到的只能报告 |
| L2 不可保证 | 单日可见作品 >约 10000、索引缺项/延迟、账号权限/地区过滤、R-18 未开、已删除作品、扫描期间新发布 | — | 只能在报告中如实标注，不能"修复" |

**关键实测依据（本次新增/更正）**：

- **Web Ajax 深翻页有硬钳制（先前的判断需要修正）**：`p=1..10` 正常返回（60 条/页），`p≥11` 会被服务端钳制回第 10/11 页附近——实测 `p=11/12/20/25/100/500/1000/20000` 对同一查询返回完全相同的 60 条（`女の子` 与 `初音ミク` 均如此）。**匿名状态单查询最多只能拿到约 600 条**，因此 Web 不能作为大窗口的枚举主力；登录态是否放宽（带 PHPSESSID）**未验证**，已列入登录后实验。
- Web Ajax 支持 `scd`/`ecd`（发布日期起止）且返回 `total`：实测 `scd=2026-11-01&ecd=2026-11-02` 返回 `total=223`，日期全部落在窗口内 → **即使只能读第 1 页，`total` 仍可用于覆盖核对**（注意匿名模式会过滤 R-18，`total` 是下界）。
- 「双向枚举」的依据是接口本身：`/v1/search/illust` 的 `sort` 同时支持 `date_desc` 与 `date_asc`（pixivpy 枚举与文档一致），每种排序各自受 offset 5000 限制；同一日期窗口两端各取 5000 条即可覆盖 1 万条以内。**待登录后实测验证**（`scripts/coverage-lab.mjs`）。
- **登录态实测（2026-11-14，`オリジナル` 标签，2025-01-01 单日）**：
  - Web 匿名 `total` = **7,957**（不含 R-18）；账号可见结果里 `x_restrict=1` 存在，说明可见集合更大；
  - `date_desc` 枚举 = **5,010 条**、`date_asc` 枚举 = **5,009 条**、两方向 **重叠 0** → 并集 **10,019 条**；
  - 边界时间戳：`asc` 最新一条 08:03（JST）、`desc` 最旧一条 14:36（JST）→ 中间仍有约 **6.5 小时的空洞**，**该日并集并不完整**。说明该日账号可见作品显著多于 10,019 条（R-18 等计入后），双向枚举不足以覆盖。
  - 结论：`desc+asc` 的上限是「2×5000」，而不是「无条件覆盖 1 万条」；是否接上必须用边界时间戳校验。
- 「双向枚举」的依据是接口本身：`/v1/search/illust` 的 `sort` 同时支持 `date_desc` 与 `date_asc`，每种排序各自受 offset 5000 限制。实测 desc 的最后一页（offset=4980）与 asc 的最后一页可用于判断两段是否接上。
- 注意：匿名 Web 搜索的 `total` 不含 R-18，而登录后的 app-api 结果可能包含（取决于账号设置），因此 **Web `total` 只能当下界，不能当等号**。

#### 3.8.4 对使用者的实际含义

- **单日可见作品 ≤5000 条**：一次 `date_desc` 枚举即可，覆盖率主要受 app-api 索引差异影响，L0 重叠去重后不会再有切片边界丢失。
- **单日 5000–10000 条**：L1a 双向枚举（+166 请求/天）可完整覆盖；是否接上由边界时间戳判定。
- **单日 >10000 条**（实测 `オリジナル` 2025-01-01 就属于这一档）：双向枚举仍有中间缺口（实测缺口约 6.5 小时）；非 Premium 账号无法保证完整。可选缓解：升级 Premium 后用 `bookmark_num_min`（服务端收藏过滤，直接只返回达标作品，绕开覆盖问题）或 `popular_desc`；或用浏览器 cookie 尝试 Web 深翻页（登录态是否放宽未验证）。
- **「能定位 id 的缺口」与「只能推测的缺口」要分开看**：前者（≤600/日，来自 Web 前 10 页差分）可以补详情并下载；后者（>600 或索引/可见性差异）无法获得 id，只能报告。二者都受「作品已删除/私有化」影响，可能进 `failed.jsonl`。
- 实测峰值参考：`オリジナル` 单日 Web 匿名计数 2025-01-01≈7,957、2024-01-01≈6,982（账号可见更高）；`女の子` 约 1,400–2,800/日；`初音ミク` 约 80–120/日 → **大部分标签单日远低于 5000，日常使用 L0 即可；只有极热门大 tag 才需要 L1a，且 >10000/日的日子需要 Premium 或接受缺口**。

| 你的目标标签单日可见量 | 决定是否需要 L1a/Premium | 用 `coverage-lab` 对目标标签+日期跑一次即可判断 |
